# Blast Radar

**What breaks if this ships?** Blast Radar answers that question against your
DataHub metadata graph, ranks the damage, and writes the verdict back into
DataHub so the next person to touch the asset sees it too.

Built for [Build with DataHub: The Agent Hackathon](https://datahub.devpost.com/).

## The problem

Someone is about to drop a column, rename a table, or retire a pipeline. The
lineage exists in DataHub, so the information needed to answer "who does this
hurt" is already there. What is missing is the ranking: a lineage graph tells
you *what* is downstream, not *what matters* downstream. Twelve consumers are
listed, two of them are a director's dashboard and a churn model, and nothing
in the UI tells you which two.

## What it does

1. Walks the downstream cone of the changed asset through DataHub's **MCP
   server** - lineage, entity metadata, ownership, and query history.
2. Scores every consumer with a **deterministic** risk model: proximity to the
   change, fan-out, consumer type, query volume, ownership gaps, and
   criticality markers. No language model touches the number.
3. Renders an impact brief: ranked table, the assets nobody owns, and a
   who-to-tell list built from actual ownership metadata.
4. Writes the verdict **back into the graph** over the same MCP surface, so the
   analysis becomes metadata instead of a message in a channel.

## Why the score is not generated by an LLM

A ranking that changes between two runs cannot go in a release gate. The score
is a weighted sum of six normalized factors, each carrying the evidence that
produced it, so a data engineer can argue with it. The optional language model
layer writes the narrative on top of those numbers and never moves them.

## Install

Requires Python 3.11+, [uv](https://docs.astral.sh/uv/), and a DataHub instance.

```bash
git clone https://github.com/voyagi/datahub-blast-radar
cd datahub-blast-radar
uv sync
```

## Configure

```bash
export DATAHUB_GMS_URL=http://localhost:8080
export DATAHUB_GMS_TOKEN=<personal access token>
export TOOLS_IS_MUTATION_ENABLED=true   # needed for write-back
```

Blast Radar launches `uvx mcp-server-datahub==0.6.0` itself, so there is no
separate server to start. The version is pinned rather than floating: this
points a subprocess at your catalog with a token in its environment and
mutations on, and the response shapes the adapter reads were verified against
that build. Point `BLAST_RADAR_MCP_COMMAND` and `BLAST_RADAR_MCP_ARGS` at a
different binary if you run your own.

## Use

Check the connection and see which tools your instance exposes:

```bash
uv run blast-radar doctor
uv run blast-radar tools --schema
```

Define the tag and property entities a publish needs, once per instance:

```bash
uv run blast-radar setup
```

Then scan:

```bash
uv run blast-radar scan "urn:li:dataset:(urn:li:dataPlatform:dbt,shop.orders,PROD)" \
    --change "dropping column promo_code" \
    --out brief.md \
    --publish
```

Without `--publish` nothing is written to DataHub; the run prints what it
would have published.

Real output against DataHub's own `showcase-ecommerce` sample catalog:

```text
order_details - 35 downstream assets, 0 critical, 16 high, 21 without an owner

 #  asset                      type       hop  score  severity  why
 1  ORDER_DETAILS              Dataset      1   61.6  HIGH      1 hop downstream; 14 assets depend on it in turn
 2  Customer Analysis          Chart        3   61.3  HIGH      Chart consumer; 3 hops downstream (2 transforms deep)
 4  Executive Summary          Chart        3   61.3  HIGH      Chart consumer; 3 hops downstream (2 transforms deep)
 6  Customer Analytics Measures Dataset     2   61.0  HIGH      2 hops downstream; Dataset consumer
11  Order Entry Dashboard      Dashboard    5   60.0  HIGH      Dashboard consumer; 5 hops downstream (3 transforms deep)
```

## How the score works

Six factors, each normalised to 0..1, each carrying the evidence that produced
it. They sum to 100.

| Factor | Weight | What it measures |
|---|---:|---|
| `consumer_type` | 30 | Where a human sees the breakage. A dashboard is not a staging table |
| `proximity` | 25 | How many **transforms** the change survives to get here |
| `fan_out` | 20 | How much breaks behind this asset, log-scaled |
| `usage` | 10 | Recorded queries referencing it |
| `ownership_gap` | 10 | Nobody to notify is worse, not better |
| `governance_signal` | 5 | Tier-1, PII, GDPR and similar markers |

Bands: 75+ critical, 55+ high, 35+ moderate, below that low.

**Proximity counts transforms, not edges.** A chart is a view of a dataset and
a dashboard is a frame around charts; neither reshapes data, so neither can
absorb a dropped column. A dashboard five edges out whose data passed through
three transforms is scored as three deep, and the brief says so: *"5 hops
downstream of the change (3 transforms deep)"*. Without this, staging tables
outrank the executive dashboards they feed, which inverts the point of the
tool.

**Unknown is not zero.** Three things can be unknown rather than absent, and
none of them are ever scored or reported as a zero: a node the walk never
expanded has an unknown dependent count, an asset whose metadata could not be
fetched has unknown ownership, and an asset whose query history was not looked
up has unknown usage. The brief keeps "nobody owns this" and "we did not
check" in separate sections, because sending someone to chase a governance gap
that does not exist costs more than saying nothing. A false all-clear is how a
table gets dropped.

**A response we cannot read is an error, not an empty result.** If the lineage
payload comes back in an unrecognised shape, the scan fails loudly instead of
rendering "nothing downstream depends on this asset. Safe to change." Only an
explicit zero total counts as an empty cone.

**Catalog metadata is untrusted input.** Asset names, owner display names and
tag labels are written by whoever has ingestion rights, and they end up in a
brief published back into the graph for other people to read. So a name is
data, never markup: characters that carry no glyph are flattened where the
metadata enters, Markdown structure is escaped in the brief, and terminal
markup is escaped in the table. Before that, an asset named `orders[/bold]`
killed the render after a scan had already published its verdict, and one
named `orders | 99 | LOW` opened three extra cells in the ranked table, so the
published brief carried a score and a severity nobody computed.

## Known limits

- When the node budget truncates a cone, **which consumers survive is
  arbitrary with respect to distance**. The budget is spent per child in
  whatever order DataHub listed that parent's lineage, so a distant consumer
  can be kept while a nearer one is dropped. A truncated cone is a sample, not
  the nearest ring. Truncation is always disclosed, in the terminal and in the
  brief; if you see that note, raise `BLAST_RADAR_MAX_NODES` rather than
  reasoning about what is missing.

- A severity tag reflects the last scan that flagged the asset. An asset that
  drops out of the flagged band on a later scan keeps its previous tag until
  something flags it again, because nothing records which assets a given scan
  tagged.
- Column-level lineage is not used yet, so the score answers "this asset is
  downstream of the change", not "this asset reads the specific column being
  dropped".
- Query history is fetched for the 40 assets most likely to top the ranking.
  Everything past that reports usage as unchecked rather than as zero.
- Brief titles are built from a URN's platform, name and fabric, so two
  entities of *different types* sharing those coordinates - a schema field and
  its parent dataset - would collide on one brief. Left alone deliberately:
  the title is the identity used to find and update the previous brief, so
  changing the scheme orphans every brief already published under it.
- The published brief escapes structure, not meaning. An asset name is
  reproduced faithfully in the text, so one deliberately written to read like
  an instruction still reads like one to a language model further down the
  chain. The brief is data about a catalog, not a prompt to act on.

## What gets written back

With `--publish`, and only for consumers scoring high or above (capped at 25
assets, because a flooded graph is a useless one):

- a severity tag, `urn:li:tag:blast-radar-high` and friends
- a numeric risk score in the `blastRadar.riskScore` structured property
- the full brief, saved as a DataHub document linked to the changed asset and
  to everything it endangers

## Tuning

| Variable | Default | Meaning |
|---|---|---|
| `BLAST_RADAR_MAX_HOPS` | `5` | How deep to walk the downstream cone |
| `BLAST_RADAR_MAX_NODES` | `400` | Node budget; truncation is always disclosed, in the terminal and in the brief |
| `BLAST_RADAR_RESULTS_PER_HOP` | `100` | Consumers requested per asset. If DataHub reports more than it returned, the scan says so rather than pretending the rest do not exist |
| `TOOLS_IS_MUTATION_ENABLED` | `false` | Mirrors the MCP server's own write switch |
| `BLAST_RADAR_DEBUG` | unset | Send the MCP server's log to stderr instead of a file |

## Everything goes through MCP

Scanning talks to DataHub exclusively through `mcp-server-datahub`:
`get_lineage`, `get_entities` and `get_dataset_queries` on the way in, and
`search_documents`, `remove_tags`, `add_tags`, `add_structured_properties` and
`save_document` on the way out. No REST, no GraphQL, no SDK.

The one exception is `setup`, which uses GraphQL because the MCP server can
*assign* a structured property but has no tool to *define* one. Skipping that
step is what produced this, from DataHub itself:

> Structured properties write rejected: no valid property assignments remain
> after removing values for non-existent properties

Writing to an undefined property soft-defines it, scoped to whichever entity
type was written first, so scores silently landed on datasets and every chart
and dashboard was refused. `setup` defines it across all seven consumer types
up front, and creates the four severity tags, since DataHub also refuses to
attach a tag whose entity does not exist yet.
